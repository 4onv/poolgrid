## Dated demand

[Sure issue #4819](https://github.com/we-promise/sure/issues/4819) was created and last updated at **November 9, 17:35:04 UTC**. It requests a bounded scaling plan that accounts for web and worker fleets sharing dependency capacity, including deployment overlap and operational headroom. This is one concrete request, not evidence of a large market. It does not establish the cause of the reported application incident, and PoolGrid does not diagnose that incident.

The [node-postgres pool-sizing guide](https://node-postgres.com/guides/pool-sizing) explains that pool limits must be considered across services and instances. The [Kubernetes Deployment guide](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) documents percentage surge rounding and warns that terminating pods can outlive the expected surge count. Those details inform PoolGrid's explicit holder model and its limitations. [Render's scaling guide](https://render.com/docs/scaling) distinguishes service replication from per-instance resources; PoolGrid does not configure either.

## Existing alternatives and direct overlap

[ConnBudget's reviewed README](https://github.com/buildyourownstuff/ConnBudget/blob/4d0055acba6217521bc7ca3c0546f4bb10ea2f80/README.md) already describes static connection-capacity analysis, rollout/scaling scenarios, manifest ingestion and PostgreSQL/PgBouncer handling. It is the closest conceptual alternative. PoolGrid contributes an original interactive matrix and explicit portable plan format; it does not invent the budgeting calculation or replace manifest discovery.

[Simplified Tools' connection-pool calculator](https://www.simplified.tools/calculate_database_connection_pool) already exposes holder choices, a budget and surge headroom. That further limits any uniqueness claim. PoolGrid combines multiple entered resources, a web/worker combination matrix, a reusable pure API and a CLI gate. These are convenience/workflow differences, not a benchmark showing superior analysis.

The comparison is selective and based on primary descriptions, not exhaustive feature testing. No competitor code or schemas were copied. The bounded JSON reader is reused from the author's own MIT-licensed project; the calculation engine, UI and plan model are original work for this repository.
